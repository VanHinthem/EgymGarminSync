# v1.1 — Generic Garmin strength activities (work in progress)

**Last updated:** 2026-10-16  
**Branch:** `feature/generic-strength-activities`  
**Status:** Read-only research + offline draft mapping implemented; CI green through `d2a2f878`. **No new Garmin write capability for generic activities.**  
**Stable version:** `main` (v1.0 behavior); keep both workflows supported permanently.

## Goal and agreed product behavior

In addition to the existing Garmin workout programs **EGYM Positief** and **EGYM Negatief** (which already contain exercise sets), support a **generic Garmin strength-training activity** started on the watch without selecting a predefined workout. After EGYM is completed, the app should match the session and propose inserting/replacing strength exercises and sets from EGYM, with explicit review/approval. No unattended Garmin writes.

**Both modes must continue working:** existing programs still correct kg/reps on existing sets; generic strength activities will need a separate insert/rebuild flow. Do not weaken the tested legacy write contract to accommodate generic activities.

Development is on a dedicated feature branch; user tests locally on Windows with .NET/Vite, without Docker/NAS.

## Actual read-only observations

User's generic Garmin strength activity: **24744752753**.

GET `/activity-service/activity/{id}`: activity type stored under `activityTypeDTO.typeKey = strength_training`, **not** `activityType.typeKey`. The root includes `activityId`, `activityName`, `activityTypeDTO`, `metadataDTO`, `summaryDTO`, etc.

GET `/activity-service/activity/{id}/exerciseSets`: root fields `activityId`, `exerciseSets`. Exactly **6 entries**:

| Zero-based indices | Type | Exercise objects |
| --- | --- | --- |
| 0, 2, 4 | ACTIVE | 3 each, all `category: UNKNOWN`, `name: null`, with `probability` |
| 1, 3, 5 | REST | 0 |

All 6 have a `startTime`. Nine nested exercise candidates in total. Existing set fields include `duration`, `messageIndex`, `wktStepIndex`, `weight`, `repetitionCount`, `exercises` and power/velocity/ROM metrics.

**Important:** generic activity is *not empty* in Garmin; watch auto-detected 3 active + 3 rest sets and returned unknown candidate exercises. We have not established whether or how Garmin accepts a reconstructed set list; the 6-set shape is read-only evidence, not a validated write schema.

Existing EGYM circuit typically has **8 exercises × 2 rounds = 16 strength sets** (excluding cycling). Thus edits to just existing set fields cannot achieve the goal.

## Code delivered on feature branch

- `src/EgymGarminSync.Web/GarminGenericStrengthInspection.cs`: loopback-only GET `/api/dev/garmin/strength-inspect/{activityId}`; authenticates to Garmin, GETs original activity and exercise-sets endpoints, reports structural metadata, identities and counts. No PUT or full personal payload output.
- `src/EgymGarminSync.Web/GenericStrengthSetPreview.cs`: loopback-only GET `/api/dev/garmin/generic-preview?egymId=...&garminId=...`. Uses cached EGYM workout + Garmin activity + sets. Maps known EGYM IDs (333,334,581,330,335,329,331,332) to Garmin category/name; skips cycling ID 31, requires two rounds, returns proposed kg/reps and existing Garmin counts, reports mapping/validation warnings.
- `src/EgymGarminSync.Web/Program.cs`: registers both /api/dev routes.
- No UI integration yet, no timestamps or durations generated, no valid Garmin replacement payload built, no generic Garmin PUT implemented.
- Matching on `main` currently filters Garmin discovery to names `EGYM Positief` / `EGYM Negatief`, and the current UI proposes matches by variant/name + time. Generic `strength_training` requires a separate, ambiguity-safe discovery/matching path.

The offline preview's mappings currently duplicate those in `ReadOnlySetComparison`; consolidate after prototyping, preserving existing behavior. Preview currently only uses cached sessions/sets, so a generic Garmin activity not yet cached will give 404. **Do not interpret this as a Garmin API failure.** Its URL is an internal developer endpoint, not a production UI contract.

Existing `GarminExerciseSetsWriteContract` and `GarminTrialPayloadNormalizer` require exactly **36 sets**, and the existing write workflow corrects fields of pre-existing sets. **Do not relax that safety contract in place.** Introduce a distinct, rigorously validated generic rebuild contract and transaction/preflight workflow.

## Next work, in order

Identify the unique EGYM ↔ generic Garmin activity safely using time window and explicit selection on ambiguity.
2. **Design timestamps and duration strategy.** EGYM provides workout/round values, but verified per-set Garmin times are lacking. Propose and label estimates instead of falsely claiming measured timings. Preserve real Garmin activity duration, heart-rate and summary.

Validate exercise identities, correct units (Garmin weight in grams), activity IDs, ordering, timestamp bounds, required fields and absence of unrelated mutations. Offline only.

5. **Preview and explicit approval UI** showing exactly which unknown/recorded Garmin sets will be replaced and estimated timing assumptions.

## Safety / constraints

- **No automatic Garmin write; no live PUT in this branch's generic flow.** Keep `GARMIN_WRITE_ENABLED=0` during analysis.
- All API interactions discussed so far for the generic sample are read-only GETs.
- Never output passwords, token files or full personal JSON payloads in diagnostic endpoints.
- Preserve current backup/snapshot, journal, approval, single-PUT guard, readback/uncertain semantics.
- Main and NAS Docker installation remain untouched until intentional PR/merge.
- Existing named-workout mode and its fixed 36-set contract remain supported in v1.1.
