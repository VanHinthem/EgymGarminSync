# Local SQLite cache — implementation phase 1

The Windows-local ASP.NET Core web API now initializes an EF Core SQLite file at
`%LOCALAPPDATA%\EgymGarminSync\sync.db`.

The database model contains:
- `CachedSession`: source, source identifier, UTC timestamp, raw source JSON, checksum, last-fetch time and summary.
- `SyncCheckpoint`: last **completed** import time and source count.
- `GarminSnapshot`: append-only data model for future original/pre-update/post-update activity+exercise-set snapshots, including hashes.

Current endpoints:
- `GET /api/cache/status` returns counts/checkpoints.
- `GET /api/cache/sessions?source=EGYM|Garmin` returns local session summaries.
- `POST /api/cache/import-initial` fetches 180 days of EGYM workouts and recent 100 Garmin activities, then persists them in one SQLite transaction. No Garmin PUT is issued.

Important limitations: **This is not incremental synchronization yet.** The checkpoint is informational and does not imply the upstream API supports modified-since. Garmin's first import saves list metadata only, not the full activity exercise sets. The `GarminSnapshot` table exists but no snapshot is captured during import; it must be populated from actual GETs before any web-based Garmin write. EGYM currently uses a raw JSON SHA-256 content identity because no immutable upstream workout ID has been verified. A revised workout may therefore appear as an additional cached entry, not a safe update. Before making the web UI use the cache as its primary source, resolve stable EGYM identity, inspect upstream incremental query support, and implement the rolling refresh window plus delayed arrival reconciliation.

`Database.EnsureCreated` supports first local development startup only; add migrations before long-term schema evolution. SQLite is local and contains personal fitness metadata; don't commit the DB, expose it to the network or persist credentials in it.

The existing web session dropdowns and comparison still use the original live read paths. Garmin writing remains disabled.


## Rolling sync prototype (phase 2)
`POST /api/cache/sync` re-reads EGYM workouts from 7 days before the previous successful EGYM checkpoint through today, and Garmin's latest 100 activities, then retains activities within the same window. All updates and checkpoints are committed in a single SQLite transaction; Garmin writes remain disabled. `POST /api/cache/import-initial` remains available for a 180-day full refresh.

EGYM records are now keyed provisionally by normalized UTC completion timestamp rather than a hash of their raw JSON, so changes to exercise details do not automatically create a different key. Duplicate completion timestamps in the same import abort the operation. Legacy hash-keyed rows that correspond unambiguously to a fetched timestamp are removed during import. This **is not a verified stable upstream ID**: a revised completion timestamp, missing timezone or older changes can still require reconciliation. Do not treat it as a definitive identity for future Garmin writes.

Garmin still exposes only list metadata in the cache. The first page of 100 activities is **not guaranteed** to cover the seven-day window for high-volume accounts, and neither API currently provides a proven modified-since feed. Treat this endpoint as a rolling refresh prototype, not complete incremental synchronization. Full set-data caching, pagination verification and immutable pre-write snapshots remain separate future work.


## Garmin full exercise sets backfill (phase 3, GET-only)
`POST /api/cache/garmin-sets/import?skip=0&take=5` fetches up to five Garmin EGYM activities from the recent-100 activity discovery list and stores the complete, unmodified `exerciseSets` JSON in a separate mutable `GarminSets` table, including its SHA-256 and fetch time. Use successive batches (skip 5, 10, etc.) and inspect `GET /api/cache/status` (`cachedGarminSets`). `GET /api/cache/garmin-sets/{activityId}` returns the cached payload only, without contacting Garmin. Import requires pre-existing Garmin session metadata in SQLite.

The first successful fetch also creates an append-only `GarminSnapshot` of kind `FirstObserved` with metadata and exact sets JSON and checksums. Subsequent imports may update the mutable cache but never overwrite this first-observed snapshot. This does NOT mean original Garmin values prior to historic modifications: the verified August 31 correction already happened. Snapshotting immediately before future PUTs still needs separate development and validation.

Existing databases are extended non-destructively with `CREATE TABLE IF NOT EXISTS GarminSets` on API start, because the initial development database was created using EF `EnsureCreated`. Formal EF migrations are still needed before production. The import currently fetches the Garmin activity list once per batch, so this is bounded backfill rather than true incremental or fully automatic synchronization. Page ordering may change if new activities appear between batches. On individual failure, earlier committed batch items stay cached; rerun the failed batch. The web comparison is not yet switched to SQLite.

## SQLite-first web UI (phase 4)
On page load the React UI reads GET /api/cache/sessions?source=EGYM and source=Garmin and GET /api/cache/status, without calling the external providers. GET /api/cache/compare?egymId=...&garminId=... compares stored EGYM raw JSON with the cached Garmin exerciseSets raw JSON. It retains per-exercise identity checks and recorded Garmin set order. The **Synchroniseren** button executes POST /api/cache/sync and reloads cached lists. Existing GET-only comparison and Garmin preview endpoints are retained; the preview intentionally validates against *fresh* Garmin values rather than trusting a potentially stale cache. Actual Garmin writes remain disabled.

Limitations: rolling sync currently updates session metadata only; it does NOT automatically refresh existing Garmin exercise-set cache entries. The existing batches endpoint is still required for set backfill/refresh. EGYM identity remains provisional and backend matching suggestion uses conservative UI heuristics until centralized matching is implemented.

## Rolling sync now refreshes Garmin sets
For every Garmin EGYM activity discovered inside the rolling overlap period, `/api/cache/sync` fetches its full exerciseSets payload, validates that an array is present and compares its SHA-256 with the mutable `GarminSets` cache. A new activity gets an initial `FirstObserved` snapshot only if none exists. Existing snapshots are never changed. Fetches complete before the SQLite transaction begins, and failures do not advance checkpoints or change cached sets. A successful response includes `garminSetsRefreshed` (number fetched, not necessarily changed). The Garmin discovery cap of 100 and the 7-day overlap still apply; edits to older workouts require explicit refresh/backfill. No Garmin PUT is enabled.


## Pre-write preparation (no Garmin writes)
`POST /api/sync/preview` still validates selected field edits against a fresh Garmin GET without saving a backup. New `POST /api/sync/prepare` accepts the same `{garminId,edits:[{setIndex,field,expected,value}]}` contract, confirms the selected Garmin activity is in recent EGYM activities, validates *every selected field* against the freshly fetched exerciseSets JSON, and stores an append-only `Preflight` snapshot with SHA-256 values. The response contains a snapshot ID and before/proposed SHA-256 digests; no proposed payload is sent to Garmin or persisted as a restore source. The snapshot includes the fresh exact exerciseSets response and locally cached **list metadata**, not an independently fetched full Garmin activity payload; this limitation matters for later full restoration. The UI exposes an explicit **Preflight-backup maken** action after selecting draft edits.

`GET /api/sync/restore-plan/{activityId}` returns only metadata, checks whether each stored snapshot still hashes correctly and whether its sets hash matches the currently cached sets. `canRestore=false` by design. A real pre-write backup must be captured again immediately before a future PUT; this earlier preflight does not guarantee the activity remains unchanged. Future restoration requires validation of the Garmin replace-all schema, fresh GET, explicit confirmation and server readback. The web `/api/sync` remains hard-disabled.

## Offline update rehearsal
`POST /api/sync/rehearse` accepts `{"snapshotId":30,"edits":[{"setIndex":2,"field":"repetitionCount","expected":12,"value":11}]}` (replace all example identifiers and values with real ones from the selected preflight and preview). It NEVER calls Garmin. It reads a `Preflight` snapshot, verifies checksums of metadata and complete exercise-sets JSON, enforces the existing draft-field validation and full-object no-collateral-change invariant, and returns hashes of the original and proposed payload without exposing the workout JSON. It reports a recovery source is present, **not** that restore can be executed. Failed integrity checks abort with conflict, and the database is not mutated. Use `GET /api/sync/restore-plan/{garminId}` to check individual snapshots and their stored hash integrity. Garmin POST/PUT and actual restore remain disabled.

This is an offline rehearsal of both weight and repetition changes, **not a Garmin API write-contract validation**. Before enabling writing, separately validate the full Garmin PUT payload schema, capture an immediately-before-write snapshot, enforce optimistic concurrency with fresh reads, and verify server readback and recovery behavior.

## Offline Garmin replace-all contract validation
The offline `POST /api/sync/rehearse` now additionally builds the *normalized 36-set replacement payload* with `GarminTrialPayloadNormalizer.Normalize` and passes it through `GarminExerciseSetsWriteContract.Validate`. It returns `replaceAllContractValid` and a SHA-256 digest of the normalized payload, without exposing the raw JSON. This reuses the structure proven by the previous controlled **weight-only** August 31 update. It does **not** establish that Garmin accepts or persists repetitionCount modifications: no Garmin PUT, subsequent readback or real restore is performed. The normalization currently requires exactly 36 sets and will intentionally refuse differently structured activities. Before a general write feature, review that hard-coded contract and validate the full activity metadata backup, transaction coordination and live rollback strategy.

## Full activity backup and offline recovery validation
The explicit `POST /api/sync/prepare` now reads both fresh Garmin resources (`/activity-service/activity/{id}` and `/activity-service/activity/{id}/exerciseSets`), validates the target activity ID and normalized complete replacement contract, then saves a new append-only `FullPreflight` snapshot of both raw responses and hashes. Earlier `Preflight` backups contain session-list metadata, not full activity JSON; they remain unchanged and distinguishable. This is a preparation-time backup, NOT the final immediately-before-PUT backup; any future write handler must re-read, validate and save a new snapshot just before issuing a PUT.

Offline `POST /api/sync/rehearse` supports existing `Preflight` and new `FullPreflight` snapshots, and independently validates a normalized replacement and a normalized restore payload derived from immutable snapshot data. Response includes `restorePayloadContractValid`, `restorePayloadSha256`, and `fullActivityBackup`. `GET /api/sync/restore-plan/{id}` exposes `fullActivityBackup` and checksum status for each snapshot. It does not claim recovery will work with the undocumented Garmin API. No writes or restore endpoints are enabled, so **a real post-PUT readback and live rollback are still untested and unimplemented**.

## Separate one-repetition restore CLI

The offline option `--offline-restore-one-repetition` does **not connect to Garmin** and validates a trial-created on-disk backup; it cannot succeed until the live-trial preparation has produced the backup folder. No automatic retries. The restore command requires an explicit backup folder path; it validates that the folder is a direct child of the local live-trials directory and that the manifest, target identity, set values, backup hashes and expected changed state match. This avoids accidentally choosing an earlier dry-run backup. An actual Garmin restore remains **untested** and cannot be guaranteed. The earlier SQLite offline rehearsal of `FullPreflight` snapshot 31 remains the pre-live verification method; the new CLI offline restore check is meaningful only after the live trial has produced its own saved folder.

## Generic web save planning (still read-only)
The web API now offers `POST /api/sync/save-plan` with `{"garminId":24032098016,"snapshotId":31,"edits":[{"setIndex":2,"field":"repetitionCount","expected":15,"value":14}]}`. It requires an existing **FullPreflight** snapshot for the exact Garmin activity, verifies the complete activity and sets SHA-256 checksums and activity identity, validates selected edits against snapshot field values, and constructs both a normalized 36-set write payload and a normalized restore payload. It returns hashes, accepted field changes, and `readOnly=true, canWrite=false, canRestore=false`. No Garmin HTTP client, database mutation, or PUT is used by this endpoint. The UI shows **Opslagplan controleren (zonder schrijven)** only after an explicit preflight backup was made; changing the draft clears the selected backup.

This is not a generalized write service yet. Before enabling a generic writer: refresh and persist a new **write-time** complete Garmin backup, enforce current-state matching/optimistic concurrency and multi-request serialization, durable write outcome and post-PUT readback, SQLite cache update only after verified readback, and explicit recoverability per activity. The hardcoded 36-set normalization remains a conservative limitation, not a guarantee for every Garmin workout.

## Guarded, generic write preparation (still no PUT)
`POST /api/sync/save-prepare` accepts the same `{garminId,snapshotId,edits}` as `/api/sync/save-plan`. It takes an in-process per-activity nonblocking lock, checks an existing immutable FullPreflight against its SHA-256 values, verifies target activity among recent Garmin EGYM sessions, fetches the complete live activity and exercise-set payloads with IPv4 transport, and compares them to the reviewed backup. On an exact match it validates the edit, normalized 36-set replacement and restore contracts, and saves a **new immutable WritePreparation** snapshot of both live resources before returning hashes and backup ID. It does not call Garmin PUT, does not change cached sets, and does not enable the existing `/api/sync` endpoint or UI save button.

In-process locks do not protect against multiple server instances, and preparation is NOT a write authorization: an eventual live writer must reacquire a durable/cross-process exclusion, perform an immediately-before-PUT final GET and consistency check, persist an outcome journal, then verify post-PUT full readback before cache mutation. On uncertain outcomes it must stop without retry. Currently there is **no generic writer or rollback endpoint**.

## Persistent write journal, first read-only slice
SQLite now contains `WriteJournal` created with a non-destructive `CREATE TABLE IF NOT EXISTS` on existing local databases. The journal records activity ID, reviewed and fresh backup IDs, status, timestamps and hashes of the complete before/candidate/normalized/recovery payloads, never workout JSON. The guarded `POST /api/sync/save-prepare` now atomically commits both its immutable `WritePreparation` snapshot and a journal record with terminal status `DryRunVerified`, returning `journalId`. `GET /api/sync/write-journal/{activityId}` exposes metadata and hashes only. `GET /api/cache/status` reports `writeJournalEntries`.

A partial unique SQLite index reserves at most one journal with active status (`Preparing`, `Ready`, `WriteStarted`, `Uncertain`) per Garmin activity. The prepare endpoint refuses to proceed if any such entry exists. The in-process semaphore also prevents concurrent preparations within this API process. **No actual write transaction is implemented, and no code creates an active write status yet.** This is a dry-run journal, not an audited record of a real Garmin PUT. Any future writer must persist its active state before issuing HTTP PUT, handle crash/timeout as `Uncertain` without automatic retry, perform a fresh final-state GET, verify readback before updating SQLite's mutable sets cache, and require explicit manual reconciliation for uncertain results. The Garmin save button and POST /api/sync are still disabled.

## Safe status-machine rehearsal
`POST /api/sync/write-simulate` accepts `{garminId,snapshotId,edits,scenario}` where `snapshotId` is an immutable **WritePreparation** snapshot and `scenario` is `Verified` or `Uncertain`. It validates backup hashes and edit/replace-all/recovery contracts, then simulates `Ready -> WriteStarted -> Verified/Uncertain`. The `Verified` scenario tests full candidate-set matching; `Uncertain` uses the original sets as the simulated readback to test failure detection. This simulator is **purely observational**: `garminHttpRequests=0`, `sqliteWrites=0`, `cacheUpdated=false`, and it does not persist simulated journal status changes. A verified simulation only reports that a future real writer *would* be allowed to update the cache after an actual Garmin readback; uncertain simulations report write blocking, but do not create a persistent lock. This is not proof of real PUT/transaction semantics.

## Persistent state rehearsal (no Garmin writes)
`POST /api/sync/journal-transition-test` takes `{garminId,journalId,action}`, where action is `Begin`, `VerifySimulated` or `MarkUncertain`. For an existing `DryRunVerified` journal, `Begin` persists `Ready` in SQLite. `VerifySimulated` changes `Ready -> SimulatedVerified`, explicitly NOT `Verified` since neither a Garmin PUT nor actual readback happened. `MarkUncertain` changes `Ready -> Uncertain`. The SQLite partial unique index and preflight guards then block additional preparations for that activity even across API restarts. This endpoint never issues Garmin network requests and never updates the cached exercise sets. Invalid and repeated transitions return conflict. The endpoint is a developer test harness, not a live writer.

**Warning**: Do not run `MarkUncertain` against a real activity in ordinary testing: it deliberately leaves a persistent blocking journal record and there is no automatic reset or reconciliation endpoint yet. The positive-path test can use a real existing `DryRunVerified` journal, with `Begin` then `VerifySimulated`. To test `Uncertain` safely, use an isolated disposable test database/activity and explicitly verify the lock after restart.

## Isolated Uncertain test harness
Run `dotnet run --project src/EgymGarminSync.Web/EgymGarminSync.Web.csproj -- --test-uncertain-isolation`. This does **not start the normal web API**. It creates a disposable SQLite file in the OS temp directory and uses synthetic activity ID 9876543210; it does not access the real user's `sync.db`, credentials or Garmin network. The test creates an immutable synthetic WritePreparation backup and two dry-run journal rows, moves the first `DryRunVerified -> Ready -> Uncertain`, closes the SQLite context, reopens the DB as an API-restart approximation, and asserts the `Uncertain` state persists, the second journal's `Begin` is HTTP 409 and stays unchanged, and the uncertain journal cannot restart. The temporary file is removed after the run.

**Recovery remains intentionally unavailable.** An Uncertain production journal must be manually investigated against the real Garmin activity and verified backups before any explicit reconciliation/clearance workflow is designed; do not simply reset it to Ready or blindly retry PUT. The harness checks persistence and re-entry safety but is not a process-kill or real network-timeout test.

## Read-only reconciliation classifier (no Garmin requests)
`POST /api/sync/reconcile-simulate` accepts `{garminId,journalId,edits,observedScenario}`. It is limited to an existing **Uncertain** journal, checks its immutable WritePreparation backup and SHA-256, reconstructs and checks the journaled candidate and full Garmin replacement contract, then classifies synthetic readbacks: `Original -> NotApplied`, `Candidate -> Verified`, and `Different -> Uncertain`. It reports hypothetical cache-update/block-clear decisions only. The source journal stays Uncertain, even if the simulated decision is Verified. Neither the database nor Garmin is contacted for writes; the API performs zero Garmin HTTP requests. This endpoint is **not** a live reconciliation nor clearance operation. To exercise it, create an Uncertain journal and real-format saved sets **only in an isolated disposable SQLite database**. Never create Uncertain on a production activity merely to run this test.

Before real reconciliation can clear a journal, it needs a genuine fresh Garmin GET of both complete activity and sets, metadata integrity checks, recovery for ambiguous/partial state, a manual explicit approval, atomic journal/cache transitions, and tests of crash/timeouts and repeated requests.

## Live read-only assessment for an Uncertain journal
`POST /api/sync/reconcile-live-readonly` requires `{garminId,journalId,edits}` for an existing `Uncertain` write journal. It validates the immutable WritePreparation backup hashes, activity identity, and reconstructed candidate against the journal hashes; then uses IPv4 Garmin auth to GET the most recent activity listing, full activity metadata and complete exercise sets. Metadata must match the saved preflight under the existing tolerance rules; otherwise the decision is `Uncertain`. Exercise sets must fully match exactly one of original (`NotApplied`) or candidate (`Verified`); any mismatch or ambiguity stays `Uncertain`. On upstream failure, return an error and leave the journal blocked. The endpoint never calls PUT, never writes to SQLite and never clears Uncertain or updates the sets cache.

**Do not manufacture an Uncertain journal for a real Garmin activity just to test this endpoint.** The existing real journal #1 is SimulatedVerified and should remain so. The live endpoint can be tested only when there is a legitimate uncertain transaction or in an isolated test environment with dedicated synthetic fixtures and mocked Garmin GET responses. Classification alone does not prove causality or authorize automatic retry or clearance; manual reconciliation design is still outstanding.

## Isolated atomic reconciliation finalization (NOT exposed as HTTP)
`GarminReconciliationFinalizer.FinalizeIsolatedAsync` is an internal integration-test helper, never mapped to an API endpoint. It takes explicitly supplied original, candidate, and observed sets plus observed activity metadata; revalidates the immutable WritePreparation backup and journal hashes; classifies the observation; and, in one SQLite transaction, changes a previously Uncertain journal to `Verified` or `NotApplied`. Only the synthetic `Verified` case upserts mutable Garmin sets cache; `NotApplied` leaves the cache untouched; `Uncertain` leaves journal and cache blocked and unchanged. Repeating closure returns `Blocked`. The disposable `--test-uncertain-isolation` harness now exercises all cases and duplicate requests.

**Security boundary:** this helper must not be mapped as an externally callable reconciliation endpoint or reused with client-supplied observations. The current test supplies simulated readbacks. A production finalizer requires a fresh trusted Garmin GET near its atomic database transition, independent confirmation, durable evidence/recovery of interrupted updates, and an approved explicit operator action. No real Garmin PUT is enabled.

## Integrated simulated write transaction (no production endpoint)
`GarminTransactionDryRun` is **internal and test-only**. With injected synthetic read and write delegates and payloads stored in a test-only registry it validates a write-time observation, durably commits `Ready -> WriteStarted` *before* invoking exactly one synthetic write, reads back synthetic results, and records `SimulatedVerified` on complete matching readback or `Uncertain` for a timeout, thrown exception, or mismatch. It never accesses the Garmin PUT transport, does not update the Garmin sets cache, and is not exposed through an API route. A duplicate invocation against a terminal/Uncertain journal is refused. The disposable `--test-uncertain-isolation` harness tests Success, Timeout, and Mismatch paths and checks write count, persisted status, and cache immutability.

**Not yet production-ready:** simulated orchestration alone does not prove crash recovery, multi-process exclusion, durable outgoing-payload storage, or real pre-PUT/post-PUT Garmin behavior. It must not be enabled for live writes until these are designed and independently tested.
